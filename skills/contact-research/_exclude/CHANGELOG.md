## 2026-09-23 — first production release: parallel orchestration; lessons from seven bulk runs (v1.0)

Seven bulk runs in September 2026 (pboone 449, darmstrong 333, jmcbroom 76, sfrench 245, apratt 436, noneassigned 37, others 543 — 2,119 contacts on Fable 5.1) hit the same problems every time. This release fixes the ones that repeated. Version numbering was rebaselined at this release: see the note at the top of this file.

1. **Parallel orchestration inside the skill** (`scripts/orchestrate.py`, `references/subagent_prompt.md`, `SKILL.md` Step 3, `state_schema.md`). Every run had rebuilt the same scratch tooling: a queue of 5-contact groups, a prompt generator, a dispatcher, a ledger with per-agent token usage, a verifier, and a stats script. `orchestrate.py` now provides `queue`, `dispatch`, `finish`, `fail`, `status`, `pack`, `verify`, and `stats`. `dispatch` embeds each contact's payload (state blocks, related records in the run, company priors) directly in the prompt file, so subagents no longer run a script to read Confidential state — the auto-mode classifier had denied that script for about a third of them. `fail` codifies the recovery used when eight agents were killed by an API 429: keep what merged, re-queue only the unmerged contacts. `stats` reports measured subagent tokens by stage and drops the chars/4 heuristic, which had underestimated real usage by about half. Recommended concurrency is 8; 16 exhausted the session's WebSearch allowance.
2. **URLs exempt from the 13–19 digit account screen** (`cr_common.screen_text`). Business Wire release IDs, SEC EDGAR accession numbers, BBB, LoopNet, LinkedIn, and Facebook object IDs in source URLs forced roughly 20 re-merges per run and cost legitimate sources. URLs are stripped before the pattern runs; the pattern is unchanged for everything else.
3. **Public identifiers stay** (`governance.md`, playbook §5, research prompt). EINs, CRDs, professional license numbers, Secretary of State entity numbers, and CIKs are published by regulators to identify the registrant and are not Restricted. Earlier runs had stripped them by hand under the minimum-data rule; the rule now says they are retained. Private identifiers of a person (account, card, government ID) remain Restricted.
4. **Domain classification** (`cr_common.PERSONAL_DOMAINS`, `derive.py`). The free-mail list was 14 domains; proton.me, pm.me, duck.com, frontier.com, earthlink.net, and family vanity domains (`thewilsoncrew.com`, `sollazzo.org`) were all classed as corporate. The list now covers privacy relays and consumer ISPs, and `derived.is_vanity_domain` catches a surname domain (a firm named after its founder is deliberately not vanity).
5. **Shared broker-dealer domains** (`cr_common.SHARED_DOMAINS`, playbook §7, `orchestrate.py pack`). `nm.com`, `lpl.com`, `ml.com`, and the like collided every run — one practice's record was offered to every other advisor on the same wirehouse domain. `pack` skips shared domains for `company_prior` and adds `company_prior_by_employer` (a record whose name matches the HubSpot employer), so colleagues on different domains still share one record.
6. **Household-pair heuristic** (`derive.py`). Skipped for IMPORT-sourced records (two rows of one import file always land seconds apart); the "no association recorded" flag is suppressed when a Spouse label already names the same person and reworded when it names someone else.
7. **Redaction lexicon and Board Confidential screen** (`cr_common.py`, `hubspot_pull.py`, `merge_state.py`, `governance.md`, `hubspot_extraction.md`). Added bereavement, prayer-request, pregnancy, caregiving, hospitalization, PIN, and wire/ACH-instruction patterns — each was hand-redacted after a subagent reported it in a bulk run. Fund IDs, children's birthdays, and ownership percentages were deliberately left out at the RM's direction: they are Confidential, not Restricted, and relevant to the research. New `signatry_insider()`: for Signatry staff and board contacts (Signatry email domain, or a Signatry-named company association with an employment or board label) the engagement screen also applies a Board Confidential lexicon and counts those hits separately. Engagement subjects are now screened as well as bodies.
8. **Smaller items.** Owner names HubSpot stores in lowercase are title-cased at pull time (`cr_common.fix_name_case`), so naming convention 3 no longer produces `dale_armstrong_…` filenames. A contact with no HubSpot owner now shows "None Assigned" everywhere the owner appears — the pulled `owner_name`, the workbook's `HS: Contact Owner` column, the PDF owner badge, and naming convention 3 filenames (`cr_common.NO_OWNER`, `owner_display()`); previously the three renderers disagreed ("Unassigned", "UNASSIGNED", and a dash). The PDF's "Recent notes" row now strips HTML and clips each note body to 400 characters (`build_profiles.clip`); a single long HubSpot note had made the row taller than a page and crashed `doc.build` with a reportlab LayoutError, which every bulk run had worked around with a pre-render scratch script. `cr_common.save_json` now writes to a PID-suffixed temp file: with eight subagents merging at once, the shared `manifest.json.tmp` produced intermittent `FileNotFoundError` races in `recount()` (seen in the 543-contact run), which the same temp name for every writer made inevitable. New `research.deceased_per_public_source` (validator accepts bool/null; workbook column, PDF About row, Summary count) — five apratt contacts were deceased per public sources while HubSpot showed them active. New `derived.role_on_fund` from the Fund association labels (holder / advisor / other) with a workbook column, a PDF DAF row, a Summary count, and a flag for advisor-only contacts, so professional advisers on client funds are not described as donors. `derived.signatry_relationship` is shown in the workbook.

9. **Health lexicon moved to stems; injury and bereavement wording added** (`cr_common.HEALTH_HARDSHIP_LEXICON`). Entries were whole words, so ordinary inflections slipped through — "surgery" did not match "surgeries" in a note describing a child's operations. Entries are now stems (`surger`, `addict`, `divorc`, `disabilit`, `alzheim`). Added from the last two runs, each traced to a record the orchestrator had to redact by hand: `memorial service`, `fractur`, `injur`, `broken bone`, `brittle bone`, `disease`, `hardship`, `ankle`, `knee`, `wrist`, `buried`, `sick`, `widowed`, `widower`. Three candidate terms were measured against 9,295 real engagement bodies and rejected: `stroke` matched only the CSS property `-webkit-text-stroke-width`, `widow` matched only the CSS property `widows:`, and `cemetery` matched legitimate grant recipients. `memorial service` is a phrase because bare `memorial` matches Memorial Day and memorial grants. The comment above the list records this so the next person re-measures instead of re-adding them.

10. **Seven more consumer domains** (`cr_common.PERSONAL_DOMAINS`). `ptd.net`, `iamotelephone.com`, `rocketmail.com`, `ibyfax.com`, `iland.net`, `bex.net`, and `reagan.com` — regional ISPs, a rural telephone co-op, a consumer mail provider, and a fax-to-email service — were each classed as an employer and each produced a company record for a domain with no company behind it.

11. **Run budgeting documented** (`SKILL.md` Step 3). Seven runs settled at about 25,000 tokens and 18 to 19 seconds per contact at 8 concurrent, with research about 90 percent of both. The number is now in the skill so a run can be quoted before it starts rather than estimated after.

## 2026-09-14 — new DAF section: fund count, tier, fund balance (v0.6)

Added at RM request: a DAF section reporting the contact's number of associated Funds, `direct_fund_balance_tier_min`, and the sum of associated Funds' `current_balance`.

1. **HubSpot pull** (`hubspot_pull.py`, `hubspot_extraction.md`). Added `direct_fund_balance_tier_min` to the contact property set, and a new pull of the Fund custom object (object-type ID `2-24861263`, property `current_balance`) associated to each contact, written to `associations.funds`. Path B connector instructions gained a matching step 6.
2. **Derivation** (`derive.py`, `state_schema.md`). New deterministic `derived.daf` block: `fund_count`, `fund_balance_sum` (sum of each Fund's `current_balance`), `tier` (the contact property, passed through as-is).
3. **Renderers** (`build_workbook.py`, `build_profiles.py`, `SKILL.md`). New `DAF:` columns (blue/HS group) on the Contact Enrichment sheet; new "DAF" section on the PDF profile, placed after "Contact".
4. **Governance carve-out** (`governance.md`). The data-minimization rule ("do not pull giving history or fund balances") previously excluded this outright. Narrowed to name the DAF aggregate (fund count, current-balance sum, tier) as the one deliberate exception — no fund names, gift/transaction history, or fund-level detail beyond the current balance is pulled.
5. **PDF header/footer** (`build_profiles.py`, `cr_common.py`). Contact Owner moved out of the "About" section and into a right-aligned header badge (mirrors the left-aligned confidence badge). Footer now reads "Skill v{version} · Model: {model} · Rendered … · Page …" — the skill version is read from `SKILL.md`'s own frontmatter (new `cr_common.skill_version()` helper) rather than hand-carried as a duplicate string.

## 2026-09-13 — spouse-corroboration rule; lexicon scoped to engagement bodies; golden file loosened (v0.5)

Follow-ups from the three-model run of the five-contact screening set on v0.4 (Fable 5.1, Opus 5, Sonnet 5 on identical Step 2 state):

1. **Spouse-corroboration rule** (`merge_state.py`, `state_schema.md`, playbook §4, prompt step 6, `SKILL.md`). One run "confirmed" a donor's spouse from a June 2024 wedding website for a same-named couple in another state and raised `household_confidence` to High on it; the other two models correctly stayed at Moderate. A public spouse source now supports High only when `household.spouse_corroboration` names a HubSpot fact it matches (`address`, `city`, `employer`, `phone`, `email_domain`, `age_band`); the validator enforces it unless the spouse came from an association label.
2. **Health/hardship lexicon scoped and word-anchored** (`cr_common.py`, `merge_state.py`, `hubspot_extraction.md`). The lexicon now applies to engagement bodies only — research prose is screened for the SSN/card/account/credential *patterns* but not the lexicon, so "medical device integrator" or a street named Terminal no longer blocks a merge (one run had to rephrase around both). Lexicon stems match at word starts (`\bdiagnos`), so "prehabilitation" no longer fires on "rehab".
3. **Golden file** (`evals/fixtures/228031919697_melanie_cook.expected.json`, `evals/evals.json`). Melanie Cook's contact score accepts `None` or `Low` (aggregator listings at the address make Low defensible); household High must cite an `address` corroboration; Andrew Cook's household is expected at Moderate.
4. **Model policy made visible** (`SKILL.md`, `cr_common.py`, `merge_state.py`, `state_schema.md`). The batch runner already routed by tier; interactive runs had no policy at all, because a skill cannot change the session's model. `SKILL.md` now states the policy (Fable 5.x default, Opus 5 for escalation, Haiku 4.5 on thin/placeholder only, Sonnet 5 not for household work) and asks the running model to check its own ID at Step 3 and warn the user before continuing off-policy. `merge_state.py` appends an "off-policy model" data-quality flag to any research fragment whose `model` is outside the policy for its tier, so the reviewer sees it on the PDF and in the workbook. Deliberately advisory — no allowlist gate.

## 2026-09-13 — determinism pass after the six-way model comparison (v0.4)

Driven by a side-by-side of v0.1 and v0.2 output for one real donor across Fable 5.1, Opus 5, and Sonnet 5: on identical HubSpot facts the runs produced High, Moderate, Low, and None, and two v0.2 runs wrote "not identifiable, 0 sources" for a donor whose spouse is a publicly documented executive. The research step had not changed between versions; the spread came from under-specification. Every change here removes a judgment call.

1. **Credential screen** (`cr_common.py`). `RESTRICTED_PATTERNS` gains two credential patterns (`password/passcode/pwd … is|:|=`, `username/login … :|=`). Two runs found plaintext portal credentials in a HubSpot donor-care thread and caught them on judgment alone; the screen now catches them mechanically. Also applied inside `merge_state.py`'s research validation via the shared `screen_text`.
2. **Two confidence scores** (`state_schema.md`, `merge_state.py`, both renderers, `research_playbook.md`, `research_prompt.md`, `SKILL.md`). `match_confidence` is the contact's own public identification; new required `household_confidence` (+ rationale) is the spouse/household. The PDF badge shows both ("CONTACT: NOT IDENTIFIED · HOUSEHOLD: HIGH"), the About section has a row for each, the workbook a column for each.
3. **Household research is mandatory, and separated** (`state_schema.md`, `merge_state.py`, renderers, playbook, prompt, `SKILL.md`). New `research.household.spouse_company` block (same keys as `company`). When a spouse or household member is known — from `derive.py`'s `spouse_in_hubspot` or from research — and the contact is Low/None, the validator refuses a fragment that leaves `spouse_company.name` null (a "Not found – <what was tried>" satisfies it). The spouse's employer never goes in the contact's own company block; the PDF gets five "Spouse's …" rows and the workbook three `Research: Spouse …` columns. This is the fix for the 0-source outcome.
4. **Fixed search recipe with stop rules** (playbook §2, prompt step 3, `SKILL.md`). Six ordered queries — name+geography, domain/handle, address, household step, company site/press, one disambiguation — each with an explicit skip condition. `None` for the contact is allowed only after steps 1–4 have run. Sources about the spouse or household company are real sources and must be listed (one run ran six searches, found the spouse's company, and recorded zero sources because it judged them "not about the contact").
5. **Step 2 completeness gate** (`batch.py`, `derive.py`, `hubspot_extraction.md`). `batch.py next` refuses (`--force` to override) to list a contact for research while `associations` lacks `contacts`, `surname_matches`, or `companies`; `derive.py` writes a flag. Three of the compared runs had an empty associations block. `hubspot_extraction.md` now carries a canonical associations fragment so hand-written connector fragments keep their shape.
6. **Tickets in the engagement pull** (`hubspot_extraction.md`, `hubspot_pull.py`, `merge_state.py`, renderers). TICKET added to both paths; the decisive facts on the compared record lived in ticket/email threads the NOTE search never returned (`num_notes=5`, zero results). Path B now also says to request email subjects first and bodies only when warranted — the screen protects state, not what the model reads.
7. **Evals** (`evals/evals.json`, `evals/fixtures/`). Eval 4 is a five-contact screening set (Cook household ×2, Johnson, Brown, New) with per-contact expectations, plus `228031919697_melanie_cook.expected.json`, a golden file for the household case; `sample_input.csv` carries all five.
8. **Batch-runner default** (`api_batch_runner.py`). Standard tier now defaults to `claude-fable-5-1`, the only model that reached both scores at High in the comparison, with the reasoning in the header and instructions to re-evaluate once the recipe has been in use.

## 2026-09-13 — model shown in PDF footer; duplicate-record candidates surfaced in the About section (v0.3)

Two reviewer-facing changes requested after comparing v0.1 and v0.2 output side by side across models:

1. **Model provenance.** `research.model` must now be the exact model ID of the model that did the research (`merge_state.py` rejects placeholders like `interactive`; `api_batch_runner.py` already filled it from the API response). `build_profiles.py` prints it in every page footer ("Model: … · Rendered … · Page n"); `build_workbook.py` adds a per-contact `Research: Model` column and lists the model(s) used on the Methodology sheet. Without this, the only way to tell which model produced a profile was the filename a person typed.
2. **Duplicate candidates as a data point, not just a flag.** `derive.py` now writes `derived.duplicate_candidates`: other HubSpot records with the same first and last name, gathered from the surname search, the contact associations, *and* the household-company members, deduplicated by ID with a `seen_in` list. Previously the duplicate check read only `surname_matches`, so a run whose surname screen came back empty (as several v0.2 runs did) silently lost the duplicate. The PDF About section gains a "Possible duplicate records" row and the workbook a `HS: Possible Duplicate Records` column; the data-quality flag is now generated from the same list.

## 2026-09-13 — fixed Path B company-association pull; added "Family"-company household detection (v0.2)

Live-tested Step 2 (HubSpot pull) against a real donor contact on the connector path and found two real gaps beyond the already-documented "connector can't read association labels" limitation:

1. **Bug**: `hubspot_extraction.md`'s Path B company-association step relied on the `associatedcompanyid` contact property, which was empty even though a real company association existed (confirmed against a live record: `search_crm_objects(COMPANY, associatedWith: contacts)` found the company; the property-based method missed it entirely). Fixed the documented method to search directly, mirroring the associated-contacts step.
2. **Gap**: The Signatry's portal uses `company.type = "Family"` as a donor-household grouping convention (not an employer). `derive.py` didn't know this and would have rendered a Family-type company as an "unconfirmed role" company — misleadingly implying employment. Added a `household` classification (excluded from `role_companies`), a new `derived.household_company` field, and a `associations.household_members` pull step (second-hop query: other contacts on that same Family company) so the connector path has a real substitute for the unreadable Spouse label. When exactly one other distinct person shares the household company, `spouse_in_hubspot` surfaces them as a probable match citing the shared company (never "confirmed" — a Family company can in principle hold more than a married couple); two or more distinct others are flagged for manual review instead of guessing.
3. Also extended the household-pair-by-timing fallback (`derive.py`) to check `associations.contacts` (already pulled in Step 2), not just other contacts in the current batch — it previously missed a directly-associated contact with a near-identical `createdate` simply because that person wasn't separately submitted as a batch member.
4. `state_schema.md` updated: `associations.contacts` entries now carry `createdate`/`hs_object_source_detail_1`; added `associations.household_members`; added `derived.household_company`; documented the confirmed `company.type` enum (`Commercial, Custodian, Family, Foundation, Grant Recipient, Prospect`). `build_workbook.py`/`build_profiles.py` updated to surface `household_company` directly instead of only inside the spouse-evidence text.

**Why it matters:** verified against a live donor record where a real "Spouse" association label existed in HubSpot (visible in the UI, confirmed by the user) but was invisible to every connector tool available — the fix means the connector path now reaches the same practical conclusion (probable spouse, flagged for review) through the household-company signal, instead of silently reporting "spouse: unknown" on a contact with a real, recorded household relationship.

## 2026-09-12 — initial version (v0.1)

First version of the skill. Enriches HubSpot contacts with public-web research through a JSON state folder, producing an enrichment spreadsheet (HubSpot data separated from inferred web data, with upload-prep sheets) and one branded PDF profile per contact.
